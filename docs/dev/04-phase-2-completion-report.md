## 1. 阶段结论

阶段 2 已形成真实可运行闭环：

- 用户可以创建、解锁和主动锁定加密保险库；
- 用户可以生成、选择、编辑、公开导出、从加密备份导入和删除真实三算法身份；

## 6. 密钥与密码安全边界

- Vault 整体认证加密，磁盘中不明文保存私钥、联系人 note 或身份 note。
- Header/KDF、AEAD、严格 CBOR、Vault ID binding 和核心密钥一致性校验全部执行。
- 错误密码、损坏备份和认证失败使用通用用户错误，无 cause 和内部密码学细节。
- UI 只使用安全视图，不取得私钥、公钥字节、KEK、Vault ID、Payload 或 Session。
- 门面消费并清零调用方密码 `char[]`；后台任务取消/窗口关闭也清除待处理密码数组。
- 新保险库与密码输入采用 8–256 个 Unicode 码点边界；所有密码框默认隐藏，并可用小眼睛临时显示或重新隐藏。
- JavaFX `PasswordField`、显示密码使用的 `TextField` 和 JVM/第三方库可能产生应用无法可靠清零的内部副本，因此只声明应用可控缓冲区的 best-effort 清理。
- 忘记 Vault 密码后无法恢复；用户只能使用仍记得密码的完整加密备份。

用户 UI 测试反馈已形成补充闭环：8/256 码点边界自动化通过，7/257 码点拒绝；小眼睛切换保持内容不变，取出密码后隐藏与显示状态均被清空。

## 7. 推迟处理的 P2

1. Windows 数据目录当前继承 `%APPDATA%` ACL，尚未额外收紧文件/目录 ACL。影响：同一 Windows 账户下运行的其它进程仍可读取密文文件，但不能绕过 Vault 密码与 AEAD。
2. 跨平台目录 fsync 与进程恰好在原子替换占位阶段崩溃时的恢复体验尚未统一。影响：Windows 已验证；其它平台的崩溃耐久性需在发布阶段补测。
3. JavaFX/JCA/Jackson/Bouncy Castle/JVM 内部副本不能保证清零。影响：应用已清理自己拥有的敏感数组，但不能提供进程内绝对清零保证。
4. 单身份独立加密导出包未实现。影响：迁移一个私钥身份需要完整加密 Vault 备份及其密码；不会影响当前安全闭环。
5. 阶段 2 未加入跨平台 JavaFX UI 自动化框架。影响：业务与安全边界由自动化测试覆盖，Windows 实际 UI 由交互式 smoke 覆盖；完整端到端 UI 自动化在阶段 5 统一建设。
6. 阶段 2 的 JavaFX 页面组合当前集中在一个 view 类中。影响：当前职责仍只限阶段 2 导航与交互，但阶段 3 不应继续向该类堆叠发送业务，应把发送页作为独立组件接入。

以上均不阻断阶段 2 的 Windows 可用身份、联系人和加密存储闭环。
