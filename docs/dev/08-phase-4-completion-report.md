# 阶段 4 完成报告：完整接收界面

日期：2026-07-24
分支：`spike/desktop-v0`

## 1. 阶段结论

阶段 4 已形成真实可运行的完整接收闭环：

- 用户可以选择本地收件身份；
- 用户可以粘贴标准 Base64 PEM 或風笺 WindBase 文本；
- 用户可以导入 binary Armor；
- 文本原样交给核心按精确 Header 自动路由，binary 显式指定格式；
- 真实核心完成严格解析、收件人路由、解密、binding 和验签；
- 只有 `SUCCESS` 会携带、预览、复制或保存 payload；
- signed valid 会展示稳定联系人、signing KID 和指纹核对状态；
- unsigned 明确展示“无法确认发送者身份”；
- 非当前收件人和无效消息均不会展示任何受保护结果；
- 新接收、失败、锁定、工作区重建或关闭时会释放旧 payload 结果。

阶段 4 可以结束；进入阶段 5 前等待用户确认。

## 5. 安全边界

- 桌面端不解析协议 wire，不推导 AAD，不执行 binding、unwrap、AEAD
  或签名算法。
- Vault 为每次操作导入短生命周期私钥 handle；可控私钥编码副本在
  `finally` 中清零，handle 由核心 lease 关闭。
- 联系人公钥必须按 KID 唯一解析；重复 KID 作为本地信任数据错误拒绝。
- 只有核心 `SUCCESS` 映射为桌面成功，失败结果结构上禁止 payload、
  发送者、message ID 和时间戳。
- 界面不展示 parser、RID、binding、unwrap、AEAD 或验签失败的内部
  阶段，也不透出底层异常 cause。
- UI 持有的成功结果显式可关闭；替换结果、失败、锁定或关闭时会清零
  其可控 byte buffer。
- 保存时只使用调用方副本，并在成功或失败路径清零；文件先写目标同目录
  临时文件，再替换目标。
- 本阶段不把真实私钥、shared secret、CEK、KEK、payload 或完整消息
  写入日志。

## 7. 推迟处理的 P2

1. 当前协议 payload 只携带 MIME，不携带原始文件名。阶段 4 跟进已
   根据 MIME 为 PDF、图片、音视频、压缩包、Office、JSON/XML 和常见
   文本建议正确后缀，未知类型才回退 `.bin`。影响：应用仍不能恢复
   原始文件名，也不能区分同一 MIME 的 `.jpg` / `.jpeg` 等等价后缀；
   用户可在保存对话框中修改。
2. 阶段 5 已增加剪贴板所有权保护：复制恢复文本 60 秒后自动清除；
   锁定、关闭接收页或处理下一条消息时提前清除；如果用户已经复制其他
   内容则不会覆盖。影响：JavaFX/操作系统在保留期间仍可能存在内部
   明文副本，无法承诺进程外绝对清零。
3. Java `String`、JavaFX `TextArea` 和系统剪贴板内部副本无法可靠清零。
   影响：应用会清除控件和业务引用，但不能承诺进程或系统内存绝对清除；
   这仍在已声明的解锁态威胁模型边界内。
4. 非文本 MIME 或非严格 UTF-8 内容不提供预览。影响：不会误解码或
   破坏字节，用户需要先保存后用合适程序打开。
5. 目标文件系统不支持 `ATOMIC_MOVE` 时回退为同目录替换。影响：仍
   避免直接写半成品目标，但不能对所有文件系统承诺原子替换。
6. 最大消息处理有忙碌提示，但没有百分比进度或显式取消按钮。影响：
   JavaFX 线程不会冻结，低性能机器上的等待体验仍可改善。
7. 原生文件选择器、保存对话框、剪贴板跨应用粘贴和超大消息的人工
   Windows 验收留到阶段 5；当前自动化不把这些声明为已人工验证。
8. JavaFX classpath 启动仍有 unnamed module 警告。影响：不影响当前
   运行，模块化与 `jpackage` 在阶段 5 统一处理。
9. macOS/Linux 的字体、文件替换和原生对话框尚未验证；当前只声明
   Windows 基线。

这些问题不影响阶段 4 的协议正确性、解密/验签、失败无 payload、
私钥保护或真实 Windows 接收主流程，不构成当前阶段阻塞。
